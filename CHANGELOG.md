# Changelog

All notable changes to this project are documented here.
Format based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning follows [semver](https://semver.org).

## [Unreleased]

### Added

- **Any block can be folded — not just list items with children.** Code fences, tables, quotes, formulas, images and multi-line paragraphs now get a collapse caret. A plain click folds, a second click expands; Alt+click folds every descendant at once.
  - **What folding looks like follows SiYuan.** A container (a list item with children) keeps its own text and collapses its children to folded rows. A block with nothing to keep — a fence, a table, a media block — is replaced by a one-line summary; click the summary to expand. A heading folds the section it introduces, up to the next heading of the same or a shallower level, and a deeper heading belongs to that section.
  - Alt is not a deeper fold level: it is SiYuan's "fold all children", which marks every descendant that has children of its own and skips the childless ones.
  - Folding is a view state over your markdown, never a rewrite: the block's text is untouched and the state is stored as a plain `collapsed::` property, so it survives a save/reload and is queryable like any other property.
  - Folding flags are hidden from the props row by default (**Settings → Hidden block properties**). Hiding is view-only — the property is still written, still parsed, still indexed, and still editable. Add your own names to that list to hide them too.
  - Turn the caret off entirely with **Settings → Fold any block**.
  - What does *not* fold matches SiYuan's own rule: a single-line block and a divider have nothing to hide, so they get no caret.

- **Consecutive top-level blocks are now separate blocks.** A heading followed by a code fence, or one table followed by another, used to merge into a single verbatim blob — so they could not be folded, moved or edited individually. A blank line now ends a verbatim region, which is what Markdown itself means by it.
  - Blank lines *inside* a construct are still content: an unterminated fence, a `$$…$$` formula, and a table's rows each stay one block, and a mixed block (an image above a fence) is untouched.
  - Two adjacent verbatim blocks are written back with a blank line between them, since two fences or two tables written back to back would merge again on the next read.
  - This is what makes per-block folding of code, tables and headings possible at all — previously a document's headings, fences and tables were one giant block.

- **A code fence with no language is no longer unreachable.** A plain ``` fence rendered a code toolbar with no language target, so there was no way to open source mode — and source mode is the only way to set a language. The label was gated on "has a language OR has a prefix", so exactly the fences that most needed a language were the ones with no way to set one.
  - The label now renders for every fence in both the reading and code-editing states. A fence with no language shows a dimmed, italic `text` placeholder — visibly a placeholder, not a language actually called "text".
  - The cursor lands immediately after the opening fence, so the language word can be typed straight in; the code body is never at risk.

- **Shift+click while editing no longer drops the block being edited.** Editing a block and then Shift+clicking another one selected only the clicked block, leaving the block you were typing in out of the range.
  - The range was anchored on the last *clicked* block, but that anchor is only ever set by a click that goes through the multi-select path — editing never does, so the first Shift+click had no anchor and collapsed to a single selection. The block being edited is now the fallback anchor.
  - Reading it inside the click handler is not enough, and this only showed up under a real instance: pressing the mouse **moves focus off the block being edited, the embedded editor fires `blur`, and the blur commit clears the focused block before the click event even arrives**. The anchor is therefore captured on `mousedown` — the last point where it still exists. Verified with an e2e probe that wrapped the live handler and logged the state on entry: it read `null` there, which is exactly why the obvious fix did nothing.
  - Plain clicks still enter editing as before, and a range grown from a previously clicked block still starts there (the click anchor wins over the edited block).

### Added

- **Tab / Shift+Tab now indent and outdent a multi-selection.** Bulk indent was reachable only from the right-click menu, so the keyboard route every outliner is expected to have was missing. Tab indents every selected block, Shift+Tab lifts it back out; unselected blocks are never touched.
  - Measured on a real instance while building this: the shortcut was dead even with the handler wired, because selecting blocks destroys the focused editor and drops DOM focus on `<body>` — and a keydown there never reaches the view's own container listener. The outline tree is now a focus target (`tabindex="-1"`, so it stays out of the Tab order) and takes focus while a selection exists.
  - Focus is re-asserted after each indent, since the operation repaints the tree — otherwise only the first Tab press would have taken effect.
  - The shortcut obeys the **Indent** group in Settings → Shortcuts, and only applies while blocks are selected and nothing is being typed: with no selection Tab is left to Obsidian's own focus traversal, and while editing it stays with the single-block indent path. Escape clears the selection and hands Tab back.

- **Extract blocks to their own page, leaving a page embed behind** (SiYuan's document block). "Move block to another page" removes the block and leaves nothing behind, which loses the reader's path — the detail is gone from the outline with no sign it ever existed. Extracting instead moves the block *and its children* into a brand-new page named after the block's own text, and puts an `![[Page]]` embed at exactly the position the block occupied, so the outline keeps its shape and the reader follows a link.
  - The page name is derived from the block text (leading list/heading markers and inline markup stripped, illegal filename characters replaced, length capped, collisions suffixed) and is offered as an editable suggestion — an empty block asks instead of inventing a name.
  - Available from the block context menu, from the multi-selection menu, and from the command palette / slash menu.
  - The destination page is created first: if that write fails, the source note is left exactly as it was. Multi-selection extracts only the outermost blocks, so a block carried inside another member's sub-tree is not written twice.

### Fixed

- **Extracting a nested block did nothing at all.** The membership check ran `doc.blocks.includes(b)`, which is only true for top-level blocks — so any block below the first level was filtered out, the extract found nothing to move, and it returned quietly. The replacement half always handled nesting correctly, which is why the embed logic looked right while the whole feature did nothing on a sub-block. Membership is now a structural check at any depth.

- **A multi-select drag spanning levels left a ghost row behind.** The repaint list was built from `blocks[0].parent` only. A selection can hold both a root block and a child buried under a different parent; every one of those lists lost a row, but only the first was rebuilt — so the other block's old position stayed rendered after it had already moved. All members' original parents are collected now.

- **One stationary member cancelled the whole group drop.** A drop was treated as a no-op when *any* member was already in place, but the group as a whole can still reorder: dragging `[a, c]` onto `b`'s lower band leaves `c` untouched and moves `a`, producing a genuinely different outline. The drop is now refused only when every member is stationary.

- **Dropping a verbatim block on empty space could escape to the root level.** The empty-space drop path computed its band from `visibleRoots`, which is not the document root list — while zoomed it is `zoomed.children`, whose members have a parent. Since a raw block is written flush-left, landing it there made it re-parse as a root block, undoing the position the user dropped it on. That path now runs its band through the same verbatim resolver the per-block path uses, and refuses the drop.

- **Cross-file drag left the moved block pointing at the wrong document.** `siblingsOf` resolves a top-level block's container through a cache set when a view registers its roots. A block that moved — especially into another note, which is what a cross-file drop does — kept its old entry, so the next delete / indent / move operated on the *old* document's block list: the block could survive its own deletion, or show up in two outlines at once. Every insertion primitive now re-points the cache.

- **Dropping into a note that is already open could silently discard the blocks.** The destination was written straight to the file, while the open view's external-change handler follows an "editor always wins" policy — it re-saves its own version and overwrites what was just written. When the destination note is open in a block editor, the blocks now go into that view's model (undoable, re-rendered) instead of behind the view's back.

- **The file-explorer drop highlight stuck to the first row hovered.** It was cleared per-element via `dragleave`, which also fires for transitions inside a row, so moving from one note to the next left the first one lit. The lit row is now tracked explicitly and cleared when the pointer leaves it or enters another.

### Added

- **Block drag & drop: reordering inside a page already worked; everything around it did not.**
  - **Across notes.** Drag a block onto any open block editor, or onto a note in Obsidian's own file explorer, and it moves there. The source note is marked dirty too — forgetting it is how a "moved" block turns into a duplicate. The drop lands as ordinary markdown, so both notes stay plain markdown.
  - **Whole multi-selection.** Dragging a handle inside a multi-selection now carries every selected block, instead of just the one under the pointer. Members of the drag group are rejected as drop targets — they are already in the payload.
  - **Verbatim blocks are draggable.** Tables, dividers, formulas and media embeds had no drag handle at all, and could not be a drop target. They now have both, with the middle band degraded to "after": a verbatim block cannot hold children, so dropping "into" a table would silently discard the dragged subtree on the next save.
  - The rules that decide all of this — band resolution, legality, no-op detection, cross-file planning — moved into `features/dragRules.ts` as pure functions and are unit-tested (16 new tests).

### Fixed

- **Dragging a block into another open note never saved the note it came from.** The destination view marked itself dirty, but the source document's block list had already lost the block and nothing said so — the source file kept the block on disk, so a "move" silently produced a duplicate. The source view now takes its own undo entry, marks itself dirty and rebuilds the sibling lists the blocks left. (The parent pointers have to be captured *before* the move: afterwards every moved block points into the destination document, and the source can no longer tell which lists to rebuild.)

### Added

- **Drag & drop: auto-scroll, source feedback, and dropping past the last block.**
  - Holding the pointer near the top or bottom edge scrolls the note while dragging, so drop targets past the fold are actually reachable. `dragover` only fires when the pointer *moves*, so this runs on an animation frame rather than in the event handler.
  - Desktop drags now dim the rows being dragged (previously only the touch path did, which made a multi-block drag look like it was moving one block), and the dimming is cleared on every exit path — including a drag abandoned outside any outline.
  - The empty area below the outline is a drop target: dropping in its upper half inserts before the first block, its lower half appends after the last one. Previously that area did nothing, so there was no way to drag a block to the end of a note.

### Fixed

- **Verbatim blocks (tables, dividers, formulas, media) can no longer be dropped into a position the file format cannot represent.** A verbatim block may only exist at the top level of a note: `serializeBlock` writes its text with no indentation, so anywhere below the root it is written flush-left and re-parses as a *root* block — the block escapes the position it was dropped on and the outline around it is reordered. Indenting it does not help either; the parser folds an indented non-list region into the parent block's text as soft lines, so the block's identity disappears instead of nesting. A drop that would need such an encoding is now resolved to a legal position: the middle band degrades to "after" (the block lands beside the target row, which is what the gesture meant), and a nested target refuses the drop outright instead of corrupting the outline.

- **Multi-block drag reversed the selection.** Dropping a multi-selection called `moveBlock` once per block, and each call inserts directly adjacent to the target — so every subsequent block pushed the previous one further out. Dropping `[a, b]` after `c` produced `[c, b, a]`, exactly backwards; the same applied to dropping into a block and to non-contiguous selections. A new `moveBlockGroup` locates the position once and inserts the group as one contiguous, ordered run. Two related corrections came with it: a group containing both a block and that block's own descendant no longer detaches the sub-tree (the descendant travels inside its ancestor), and if any member cannot be placed legally the whole drop is refused rather than moving part of the selection.

- **Touch drags ignored the multi-selection.** The pointer-based fallback carried a single block, so a long-press drag moved one block even with several selected. It now carries the whole selection like the desktop path, and the floating ghost reads "N blocks".

### Added

- **Typed blocks, SiYuan-style: every block knows what it is, and any block can become any other type.** Until now a block was either an outline bullet (`kind: 'list'`) or an opaque verbatim markdown region (`kind: 'raw'`), so a heading, a callout, a code fence and a table were indistinguishable to the editor — the only way to change one was to retype its markdown by hand.
  - **18 block types** — paragraph, heading, task, quote, callout, code, math, table, bullet list, numbered list, divider, footnote, image, video, audio, embed, HTML, properties. The type is **derived from the markdown on every read**, never stored: there is no `type::` property to drift out of sync, and the file stays plain markdown.
  - **Conversion** between any two types: strip the current type's syntax, then wrap the content in the target's. Heading level, callout kind (`note` → `warning` → …) and fence language survive a same-type conversion, so "make this a heading" keeps what was already there.
  - **Entry points everywhere**: a type badge in the gutter (hover to reveal, click to convert), a "Block type" entry in the block context menu, and a "Change block type" command. The menu also carries the *parameters* of the current type — heading level 1-6, callout kind, code language.
  - **Media blocks**: "Media block" picks an image / video / audio file from the vault and writes a standard `![[path]]` embed; the block's type follows from the extension.
  - The slash menu now derives its block-type entries from the same metadata table, so a new type only declares its template once.

### Added

- **A SQLite secondary index over the vault: markdown stays the source of truth, the database is a rebuildable cache of it.** Queries, backlinks and supertags all run off an in-memory index that is thrown away and re-walked on every vault event, which makes anything that needs a join (or a large scan) awkward to build and impossible to inspect. The plugin now also maintains a real SQLite database (wa-sqlite, compiled to WASM and embedded in `main.js`, running on a memory VFS) with tables `files`, `blocks`, `props`, `tags`, `links`, `refs` and `page_props`.
  The contract is one-way by construction: **every row is derived from the .md files, and nothing ever writes to a note.** Three consequences:
  - **Rebuildable.** "Rebuild the SQLite index from markdown" drops every table and re-derives them from the vault; a snapshot that fails `integrity_check`, or one written by an older schema version, is discarded and rebuilt the same way.
  - **Syncable.** The `files` table records each file's `mtime`, `size` and a content fingerprint. "Sync the SQLite index with the vault files" diffs the vault against that table and re-reads only what moved — which also catches edits made by other apps (sync clients, git, external editors), not just edits made inside Obsidian. A rename is a forget plus an index; a delete removes the file's child rows too. Auto-sync is on by default and re-indexes a single file (debounced) when it changes.
  - **Verifiable.** "Check the SQLite index against the files" re-reads every file and compares its fingerprint with the one stored when it was indexed, reporting drift that `mtime`/`size` cannot see (same timestamp, different bytes).
  A **SQL console** ("Open the SQLite index console") runs ad-hoc SQL against the index with sample queries for blocks per page, open tasks, tag usage, most-linked pages, block references and property values; Rebuild / Sync / Verify are one click away.
  Both indexes now come from ONE extractor (`src/index/fileFacts.ts`), so the in-memory index and the database cannot disagree about what a file means. Settings: enable the index, keep a snapshot on disk (default on — restarts then only re-index what changed), and auto-sync.
  *Implementation note:* wa-sqlite's Emscripten glue reads `import.meta.url`, which is empty in a CJS plugin bundle and makes it throw before it ever looks at `wasmBinary`; the build defines it away and passes the compiled SQLite as bytes, so the plugin fetches nothing at runtime and still ships as a single `main.js`.

### Changed

- **Block-property rows align with the block TEXT (Logseq parity).** The `key:: value` row under a block used to sit at the bullet column's left edge and — on blocks with children — BELOW the children. It now indents past the bullet column AND the content padding so the property text starts exactly at the block text's x (bullet column and content padding are shared CSS variables, `--lgp-controls-w` / `--lgp-content-pad`), and the row is inserted directly under the block text, before the children.
- **Collapse carets are hover-revealed and take no layout space (Logseq feel).** The fold arrow used to sit in the document flow (16px column) and stay visible on every parent block, so rows without children had to compensate with a placeholder. The caret now floats absolutely over a reserved slot inside `.block-controls` (which every row renders) — it takes zero layout space, the bullet column stays aligned across sibling rows, and the arrow appears only while the row is hovered (with a soft opacity transition). Blocks whose children are COLLAPSED keep the caret always visible so the folded state stays discoverable; touch devices without hover also get it always visible. Applies to the in-place block-embed rows too (same `.block-caret` chrome).

### Added

- **Prolog queries: a logic query language with variables, joins and recursion, plus a visual query builder.** `{{query ...}}` has a fixed vocabulary (marker / tag / page / text / date), which cannot express "blocks tagged #book whose author also wrote something tagged #film" or "everything under a heading that has a deadline" — those need variables, joins and recursion. A ```prolog fenced block now runs as a query:
  ```prolog
  % Facts: block(Id, Text) in_page(Id, Page) tag(Id, Tag) prop(Id, Key, Value)
  %        link(Id, Page) ref(Id, ToId) parent(Child, Parent) task(Id, Marker)
  % Rules: ancestor(X, Y)  has_tag(Id, Tag)

  ?- tag(B, book), prop(B, author, A).
  ```
  Results render as a table directly under the block, one column per variable in first-appearance order, and re-run whenever the block or the vault index changes. Cells holding a block id are clickable and jump to that block. The block can define its own helper rules above the `?-` goal, layered over the fact base. **The query is plain markdown**: it is a RENDERING of the vault, not a storage format, so removing the fence leaves the note exactly as it was and saving never rewrites the query (covered by a test). Only TOP-LEVEL fences are queries — an indented fence is absorbed into its parent bullet by the parser.
  The interpreter (`src/features/prolog.ts`) is a real Prolog subset: an operator-precedence parser up to `:-`, unification with an occurs check, SLD resolution with backtracking, cut (`!`, correctly scoped to its own clause and opaque inside `\+`, `call/1` and `findall/3`), if-then-else, and built-ins (`findall/3`, `member/2`, `append/3`, `length/2`, `between/3`, `sort/2`, `msort/2`, arithmetic via `is/2`, comparison, and the type and string predicates). Deliberately absent: `assert`/`retract` (the fact base is rebuilt from the index, so a query can never mutate the vault or carry state across renders) and anything touching files, shell or network. Every run is bounded by inference steps, recursion depth and result count, so a runaway query reports a limit instead of hanging the editor.
  **Case rule:** an uppercase token is a VARIABLE, so tags, page names, property keys and markers are stored lowercased (`task(B, todo)`), while property values and block text are verbatim and need quoting when they start uppercase (`prop(B, status, 'Open')`).
  The **visual builder** (command "Build a Prolog query (visual builder)", also reachable from the slash menu) removes the vocabulary barrier: pick a predicate from a dropdown of the real ones, set each argument to a variable (which joins across conditions) or to a literal (with autocompletion from the values actually in your vault), negate any condition, and watch the generated Prolog and a live result preview update as you edit — then insert it. Built-in `ancestor/2` and `has_tag/2` ship with the fact base, and schema predicates always exist, so a vault with no deadlines gives "no results" rather than an error.
- **`view::` on a parent block renders its children as a table, cards, or tabs.** An outline forces every child to be a bullet, which makes a list of same-shaped records unreadable — you cannot scan a column, and the fields you want to compare sit at different indents. Now a `view::` property on a PARENT block changes how its children are presented:
  ```markdown
  - Books
    view:: table
    - Dune
      author:: Herbert
    - Solaris
      author:: Lem
  ```
  The same indented markdown renders as a **table** (one row per child, one column per property), as **cards** (a responsive grid, each card listing all fields), or as **tabs** (child names as tabs, the selected record below). Aliases are accepted (`card`/`cards`/`gallery`, `tab`/`tabs`/`accordion`, `grid`/`list`); an unknown name falls back to a table rather than rendering nothing, and a view on a childless block shows an explicit empty state instead of looking broken. **The data is untouched** — a view is a RENDERING of ordinary indented blocks, not a storage format, so removing the property restores the plain list and the file round-trips byte-identically (covered by a test). Columns are derived from the children in first-seen order (so the table reads like the outline does); `view-columns:: year, author` overrides that with an explicit order or subset. A child that has children of its own contributes ONE record rather than a nested expansion — zoom into it to reach its subtree. Every row, card and tab is clickable and zooms into that block, so a view is never a dead end, and the tabs view remembers the selected tab across re-renders. Capped at 200 records (the same ceiling `{{query}}` uses) with the overflow reported. `view::` and `view-columns::` are config, so they never appear as data columns of their own. Pure view-model logic in `src/features/blockViews.ts` (unit-tested), DOM in `src/blocks/blockView.ts`.
- **Supertags: a tag can carry a field template (Tana supertags / Logseq DB new tags).** A tag whose own page declares properties becomes a **supertag** — the page IS the definition, exactly as Logseq DB's new tags work, and with no new syntax: `Person.md` holding `lastname::` / `birthday::` / `extends:: #Contact` turns `#Person` into a structured type. Applying such a tag to a block materializes the inherited fields as ordinary `key:: value` block properties; a field with a value is a **default** (filled in on apply), an empty one just declares the field. **Fields are only ever added, never overwritten** — a value you already typed is never clobbered by a template, which is the one thing a template feature must not do — and applying twice changes nothing. `extends::` inherits, transitively and cycle-safe, with a child overriding a parent's default in place and a diamond contributing each field once. Opening a supertag's own page now shows a **collection table** of every block carrying that tag (Tana's tag page / Logseq DB's automatic per-tag table), with columns taken from the *resolved* template — inherited fields first — so the table stays stable as instances vary; clicking a row jumps to the block. Commands `Apply this page's supertag to the focused block` / `Remove this page's supertag…` do the materializing and retract it. Removing a tag drops only the fields it contributed that are still empty or still hold the template default — **anything you filled in survives**, as do fields another tag on the block still requires. Note that field names are Logseq property keys (`[A-Za-z][A-Za-z0-9_-]*`): `lastname::` is a field, `last name::` is not. Logic lives in the pure, unit-tested `src/features/supertags.ts` (templates/inheritance/apply/remove), `supertagText.ts` (which `#tag` occurrence a removal touches) and `supertagCollection.ts` (the table model).
- **Filter the page's linked references (Logseq parity).** The "Linked references" section at the bottom of a page gets Logseq's funnel button next to the reference count: clicking it opens a dialog listing every page reference occurring inside those references (`[[Page]]` and `#tag` alike — Logseq treats both as page refs), each with its occurrence count, narrowed by a search box. Clicking a value **includes** it, Shift-clicking **excludes** it, and pinned values move into Includes / Excludes rows (click one to drop it) with a "Clear all filters" footer. Matching follows Logseq's `matches-filters?` exactly: **include is AND** (a reference survives only if it carries every included value) and **exclude is NONE** (any excluded value hides it), where "carries" means the reference's *effective* refs — its own links and tags, everything inherited from its ancestor blocks (a child of a linked block is linked too), and the page it lives on, so a filter can also select by source page. Candidates come from the UNFILTERED set so the list doesn't shrink while you pick values, the funnel is colored by state (neutral / green includes / red excludes / amber both), the count reads "N of M" while filtering, and a filter that hides everything says so instead of looking like "no references". The filter is stored per page in the plugin settings (`refFilters`, sanitized on load), so it survives re-renders, file switches and restarts. Matching logic lives in the pure, unit-tested `src/features/backlinkFilter.ts`.
- **TraceTime parity: each outline row shows its last-edited timestamp.** The TraceTime plugin ("Show when each block of a note was last edited") only decorated native editors — its CM6 overlay is built on a whole-file document and its cleanup evicts files not open in a native markdown view — so the block editor showed nothing. The outline now renders TraceTime's own `.tracetime-label` component at each row's right edge (same dot/text component, same relative/absolute formatting, driven by the plugin's settings), fed from the plugin's tracker: outline blocks are matched onto the tracker's index by normalized-text runs (indentation is erased by the shared normalization, so any depth matches), labels refresh right after a save's disk write triggers the plugin's reconcile, and rows re-resolve on every render. Requires the tracetime plugin; per-item granularity for blank-less outlines comes from our tracetime fork 0.2.0 (upstream merged consecutive list lines into one timestamp until a blank line — the fork splits every list line into its own block and stops edit windows at list boundaries).
- **Page source mode is now Obsidian's own native source mode.** The status-bar mode menu's middle entry switches the leaf to the native markdown editor with `mode: 'source'` — the whole file as raw markdown, nothing rendered, exactly the native editor's source mode. The previous implementation kept the block editor and only changed what happened when clicking INTO a block (the editor mounted without live preview), so the page itself never displayed as source. The chip now reads the native view state (`getMode()` + the `source` flag), and the in-place flip between source mode and live preview bypasses the take-over patch so the file is not bounced back into the block editor; the file content is never touched by mode switches. The per-block "Source mode" escape hatch (one raw edit session from the context menu) is unchanged.
- **Page properties editor setting: Logseq text or Obsidian's native properties UI.** The page-properties first block can now be edited through Obsidian's REAL native properties editor component (the `.metadata-container` the native markdown view renders above its content): native look (the row drops its bullet and drag-handle chrome), native property type widgets from `metadataTypeManager`, and every property plugin that extends the native properties UI works unmodified. The component class is grabbed off a live instance (any open markdown view; when none is open — take-over mode — a native view is flashed in a new tab for exactly this purpose and detached again) and hosted with a small owner shim whose `saveFrontmatter` round-trips the record into the page's OWN format: file-top `key:: value` lines for Logseq-format pages (page-props registry + metadata-cache merge follow, so an `editor::` change is honored on the next open) and a `stringifyYaml` dump of the frontmatter body for Obsidian-format pages. Deleting the last property removes the props block; the file format never converts either way. The editor instance is cached per file, re-parented across re-renders, re-synchronized from the block model on mount, and torn down on file switch/close.
- **Per-page default editor: the `editor` page property decides whether a document opens in the block editor or the native editor (`editor:: logseq` / `editor:: native`).** The property is read from Logseq-format page properties (file-top `key:: value` lines) or frontmatter (`editor: native`), key and value case-insensitively; any other value falls through to the settings. It is the most specific signal and overrides the take-over settings in both directions: `logseq` forces the block editor even with take-over off or outside included folders, `native` keeps the native editor even inside included folders — without the property the settings decide exactly as before. It only sets the DEFAULT: the manual switches (status-bar mode menu, "Open current file with the native/block editor" commands, ribbon icon) still work from either side and are never bounced back by the property. Logseq-format properties resolve from the page-props registry, which the block index now populates vault-wide on every scan (layout-ready + debounced create/modify/rename rebuilds) — previously the registry only held files opened in the block editor, so a never-opened file's properties (including the `editor` one) were invisible; deleted/renamed files drop their registry entry via the index. Frontmatter resolves through Obsidian's metadata cache. Both lookups are synchronous map/cache reads, so the setViewState take-over patch stays cheap and view creation is never delayed. Changing the property inside the block editor (props block or page-source mode) takes effect on the next open of the file. Decision logic extracted into pure, unit-tested helpers (`editorChoiceFromProps` / `takeOverForFile` / `docPageProps`).
- **The outline guide line hangs under the bullet and folds children (Logseq behavior).** The vertical line beside a block's children used to start at the row's left edge, visibly left of the bullet dot it belongs to. It now runs centered under that dot — starting just below it and stopping short of the last child's dot, with a small gap on both ends — and is clickable: clicking the line folds the block's children, clicking the stub again unfolds (the stub stays visible while collapsed as a second affordance next to the caret, with a widened hit area so the 2px line is comfortable to hit).
